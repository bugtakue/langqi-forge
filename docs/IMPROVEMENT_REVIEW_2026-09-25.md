## 已复现的缺陷：读到却未交付

使用我们自己官方 GitHub 运行下载中的公开 requirements.yaml，按原配置编译第一批四个需求：初始上下文 23,801 字符；一次并行读取四个规格首页后变成 42,457 字符，触发原 32,000 字符上限。压缩后只有 26,401 字符，但四个工具结果都被丢弃，下一次模型请求包含零个工具结果；第二轮仍可复现。游标已前移，模型却没看过对应正文。

这是确定性协议复现，不是模型能力测试；证明了一个代码缺陷，尚不能证明首轮的每次失败都由它导致。

修复：

1. 先为新观察预留空间，再填可选源码快照。超出滚动软限时，也必须把刚读到的正文与对应 tool-call 成对交付至少一次，不能仅凭游标宣称内容已读。
2. 不为保留观察而保留模型已经生成的大段写文件参数。仍保留原始密封轨迹，输出长度、工具次数和网关请求大小限制仍有效。
3. 默认滚动上下文从 32,000 调到 96,000 字符，使真实规格与当前源码有共存空间；这可能增加单次输入成本，必须用正式运行比较，不声称已经更省 Token。
4. stdout 镜像脱敏、限长的批次、工具失败、压缩、校验和终止信息，不镜像原始 prompt、源码正文、模型响应或密钥。日志故障不改变运行结果。

修复后对同一公开规格做同样的协议捕获：第二次请求实际携带 4 个工具结果（42,481 字符），第三次携带 8 个（60,611 字符）；新增四页并行读取回归也在强制 16,000 字符软限下通过。模型循环原有 31 项测试通过。本轮完整 146 项测试中，3 项因本机浏览器环境跳过，1 项遇到临时端口 EADDRINUSE；该端口检查用例单独复跑通过，其余测试通过。保留该环境竞争失败，不将它隐藏为从未失败。

随后完整复跑：`python -m unittest discover -s tests -q -b`，146 项 / 143 通过 / 3 跳过，54.105 秒，无失败。上述临时端口竞争历史仍保留。

诊断快照 `f570b78` 已在 ARC-Bench 保存，尚未启动任务；它只增加日志。后续评测使用包含上述压缩修复的新快照，不重复花费额度验证已复现的错误版本。

## 复测结束与效率优先修订

`4f394fa6ab49` 最终失败，平台时长 26m46s、得分 0.0。日志确认模型写入六个应用文件并修复一次 JavaScript 语法错误，quick 构建通过；随后网关第二次尝试返回 HTTP 400，触发熔断。代理报告 14 次成功模型请求、零次浏览器探针、没有晋升的实现批次。因此直接终止原因是网关错误，**不是**回合耗尽；旧日志不含提供商错误类别，不能推定 400 的唯一根因。

本轮只做直接相关的修订，不新增多代理架构：

- 保留模型返回的 `reasoning_content` 协议字段，包括压缩时保留的 assistant/tool 配对。此前两处会丢弃该字段；[DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)明确要求工具会话续传该字段。修复兼容性缺陷不等于已经证实旧运行的具体 400 原因。截断输出不再伪造一条没有提供商续接字段的 assistant 消息。
- HTTP 错误正文只在内存读取上限 64KB，映射为固定类别（reasoning/tool protocol、context limit、unsupported parameter、quota/capacity 或 unclassified），不记录或返回正文。400 仍不盲目重试，安全限制不放宽。
- 批次保持完整需求和依赖顺序，除了最多四项，增加默认 32,000 字符公开规格软限；单个超长需求不截断。对本队下载的公开 GitHub 需求，首批从 41,280 字符四项变为 23,182 字符两项，47 项全覆盖，计划从 12 批变为 17 批。24,000 字符方案会增至 23 批，故未采用；32,000 仍可能增加总成本，须以真实成绩比较，不能直接宣称更省。
