# 智能体与验收框架

一次运行只做四件事：按依赖图排批次，把当前批次的上下文交给模型，在批次内循环改代码，再由验收决定这段改动能不能留下。

入口是仓库根目录的 `main.py`。它调用 `factory26_harness.qualifier`。运行时读取主办方给出的 `requirements.yaml`，在输出目录写出 `frontend/` 和 `backend/`。模型通过工具改这两个目录里的文件。

## 图

`requirements.flatten_atomic` 读出原子需求，并按原子依赖和文件夹顺序做稳定拓扑排序。后一个需求不能排到它依赖的需求前面。`architecture.describe_run` 再按批大小和规格字数把这条顺序切成批次。

GitHub 公开需求是 47 个原子。表格公开需求是 24 个原子。同一文件夹的说明在一批预算里只计一次，并在提示里单独给出一次，短需求不必再为这段共享说明逐条翻页。注册、登录、找回和退出四条原文可以放进同一次提示。所以同组需求留在同一轮循环，而不是被重复的上下文拆开。整任务索引在 8000 字以内，这两题的索引都覆盖全部需求编号。

某个需求失败后，直接依赖它的后续需求不再交给模型，并记入失败。文件夹顺序只决定先后，不额外制造失败边。

## 上下文

每一批只给模型四块未信任数据：

1. `task_outline`：整题的编号、名称和依赖，用来避免把后面的需求设计死。它不把别的批次派给当前批次。
2. `current_batch_graph`：当前批次要做的编号、批内依赖，以及已经排在前面的依赖。已经验收通过的编号单独列出。
3. `current_batch_specs`：当前批次的规格。短规格直接放进提示；被缩写的规格要先用 `read_requirement_spec` 读完。
4. `prior_source_paths`：前面批次已经改过的路径。
5. `prior_batch_handoffs`：前面批次留下的状态、接口和导航摘要。采用前要对照当前源码。

规格、文件、工具输出和交接摘要都是数据。它们不能改写验收规则，也不能让模型写到 `frontend/` 和 `backend/` 以外。

## 循环

一批里面的会话按这个顺序推进：

`read_or_edit` → `quick_validation` → `browser_probe` → `acceptance_audit` → `audit_pass`

还没改文件时继续读和写。改完先跑 quick 校验。检查失败后的修补看到同一张当前批次图和整题索引，只改失败点。再做带可见文本断言的浏览器探测，然后对照当前批次做验收。验收通过的唯一收尾是一条以 `AUDIT PASS` 开头、不再调用工具的摘要。连续三轮只有说明、没有被接受的进展，会话进入 `stall` 并结束这一批。

默认每批最多 20 轮。提示里留出校验、探测、修补和验收的轮次。单批写不完就失败，不把未改动的脚手架当成完成。

## 验收

验收不相信模型自己说完成。一批改动先写在隔离副本里：

1. 开跑前检查通用脚手架能构建、能启动。
2. 模型改动留在临时副本，失败的尝试不进入下一批。
3. 独立检查通过后才允许保留。
4. 检查失败时，在同一副本里做有限次修补。
5. 浏览器探测要覆盖当前修订。
6. 依赖失败的需求直接阻断。
7. 已经通过的浏览流程可以在后续批次重放。
8. 检查通过才提升到输出目录，否则丢弃这份副本。
9. 一轮下来没有任何批次完成，拒绝留下未编辑的脚手架。

计划写在输出目录的 `.arc/compiled-plan.json`。路线是 `model-generated-implementation`。正式入口先跑模型，这一批最多 8 轮，然后对匹配到的公开画布做一次恢复。恢复名称写在轨迹里，`task_specific_prebuilt_code` 记为 true。报告里的 `architecture` 字段是上面四层的当次记录。
